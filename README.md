# Риск платежей и прогноз нагрузки

Проект на Python и PostgreSQL воспроизводит офлайн-эксперимент для платёжного сервиса. Он собирает SQL-витрины, сравнивает два почасовых прогноза на трёх рядах, выделяет аномальные часы и выбирает модель риска и пороги автоматического решения. Файл `report.html` содержит результаты прогона, графики и бизнес-интерпретацию. Первый запуск использует синтетические данные.

Готовый пример за 42 дня включает обе обученные модели, SQL-витрины, решения по транзакциям и прогнозы. Команды для сверки отчёта приведены в [инструкции к артефактам](artifacts/README.md).

## Быстрый запуск

Распакуйте архив и откройте в терминале каталог, где лежат `pyproject.toml` и `compose.yaml`. Установите Python 3.12 и Docker с Compose. Команды ниже даны для Bash и запускают PostgreSQL 16 локально.

```bash
docker compose up -d --wait
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -e .
export PAYMENT_RISK_PG_DSN='postgresql://payments:payments_dev@127.0.0.1:5432/payments'
python -m payment_risk --days 42 --out results_smoke
python -m unittest discover -s tests -v
```

Откройте `results_smoke/report.html` в браузере. Для полного демонстрационного прогона выполните `python -m payment_risk --out results`. Отчёт автономный и включает графики. Файлы CSV, Parquet и JSON позволяют перепроверить расчёты. Список параметров доступен через `python -m payment_risk --help`. Используйте новый каталог для каждого сравниваемого прогона. После проверки `docker compose down` остановит контейнер.

В PowerShell создайте окружение командой `py -3.12 -m venv .venv`, вызывайте `.\.venv\Scripts\python.exe` с нужными флагами `-m` и задайте переменную командой `$env:PAYMENT_RISK_PG_DSN = 'postgresql://payments:payments_dev@127.0.0.1:5432/payments'`.

### Подключение к своему PostgreSQL

Используйте `PAYMENT_RISK_PG_DSN` со своей строкой подключения. Флаг `--pg-dsn` переопределяет переменную при запуске CLI. Запуску нужны права подключения к базе и создания временных таблиц. Проект загружает данные через `COPY` во временную таблицу, выполняет запросы и выгружает Parquet и отчёт в каталог `--out`. Временные таблицы удаляются при завершении сессии. Учётная запись из `compose.yaml` предназначена для локального демо на `127.0.0.1`.

Если порт `5432` уже занят, запустите `PAYMENT_RISK_POSTGRES_PORT=5433 docker compose up -d --wait` и замените `5432` на `5433` в строке подключения.

По умолчанию генератор строит 98 дней с 6 января 2025 года в UTC, использует seed 42 и добавляет воспроизводимые аномальные часы. Модель обучается на окне до 10 марта, валидация длится до 24 марта, тест заканчивается 14 апреля в 00:00 UTC. Границы периодов исключающие. Операции в часе, ещё не завершившемся на момент выгрузки, исключаются из прогона.

## Запуск со своими данными

```bash
python -m payment_risk \
  --input transactions.csv \
  --train-end 2025-03-10T00:00:00Z \
  --validation-end 2025-03-24T00:00:00Z \
  --observation-end 2025-04-14T00:00:00Z \
  --out results_real
```

Принимаются CSV, CSV.GZ и Parquet. `--observation-end` задаёт момент выгрузки, на который считаются доступными исходы. Границы обучения и валидации проходят по полуночи UTC. При пропуске границ проект вычисляет их из доступного диапазона. Нужны как минимум 21 день для обучения, 6 для валидации и 3 для теста, а также созревшие метки обоих классов для обучения и валидации. Необходимо единое денежное измерение. Суммы и штрафы выражаются в одной валюте.

| Поле | Тип и смысл |
| --- | --- |
| `transaction_id`, `user_id`, `card_id`, `merchant_id` | Непустые идентификаторы. `transaction_id` уникален после удаления точных дублей. |
| `event_ts` | Время попытки платежа. Используйте ISO 8601 с явным смещением. Метки без смещения трактуются как UTC. |
| `merchant_category`, `country`, `channel` | Категория мерчанта, страна и канал, известные до принятия решения. |
| `amount` | Положительная конечная сумма попытки. |
| `status`, `status_available_at` | Статус после авторизации и время его появления. Для исторического decline rate используются только доступные финальные `approved` и `declined`. |
| `is_fraud`, `label_available_at` | Метка подтверждённого fraud/chargeback 0 или 1 и время, когда стал известен исход. Пара пустая для неизвестного исхода. Ноль требует подтверждения по завершении окна наблюдения. |
| `operational_risk_flag` | Бинарный сигнал мониторинга, доступный при попытке или к закрытию её часа. Сумма флагов образует отдельный прогнозируемый ряд. |

Для CSV используйте столбцы с этими именами. Поддерживаемые значения статусов и правила обработки категорий описаны в `src/payment_risk/data.py`. Для редких категорий словари строятся только на операциях до границы обучения.

## Витрины и признаки

- **`hourly_mart.parquet`** содержит строку на каждую пару UTC-часа и категории. Пропущенные пары получают нулевые счётчики и суммы. В числе признаков объём попыток, суммы, число уникальных пользователей, доля declines по всем попыткам и по известным финальным статусам, риск-сигналы, `LAG` и rolling-агрегаты прошлых часов. Уникальных пользователей нельзя складывать между категориями для метрики по всей платформе.
- **`transaction_mart.parquet`** содержит одну строку на попытку. Для пользователя считаются count, sum и average за 1 ч, 24 ч и 7 дней и секунды с предыдущего отличающегося времени операции. Для карты считаются уникальные страны и мерчанты, исторический средний чек, разность и стандартизованное отклонение. Для мерчанта считаются объём и средний чек за час, доли declines и сегмент по последним 7 дням с минимумом в 20 известных финальных исходов. Объёмы истории берутся из `[T − W, T)`. Платежи с одинаковым `event_ts` не входят в историю друг друга.
- **Доступность исторического статуса.** SQL представляет каждую финализацию как интервал, в котором статус видим в rolling-окне. События входа и выхода накапливаются через `SUM OVER`. Это обеспечивает точный point-in-time расчёт при задержке статуса и на границах окна. Часовой статус считается известным, если его время строго меньше конца часа.
- **Допустимые поля модели.** Модель получает столбцы `f_*`. Метка, её дата, текущий статус, сигнал мониторинга и сырые идентификаторы хранятся отдельно. Календарные признаки рассчитаны в UTC. Средние, стандартные отклонения и возраст истории могут оставаться пропущенными при холодном старте.

Тексты запросов PostgreSQL расположены в `src/payment_risk/sql/hourly.sql` и `src/payment_risk/sql/transactions.sql`. Для обычных rolling-признаков используются окна `RANGE`. Уникальные страны и мерчанты по карте считаются в `LATERAL` по индексу на идентификаторе карты и времени. Для отдельной проверки витрин после полного прогона передайте сохранённую очищенную таблицу и границы прогона в `build_marts`.

```python
import json
import os
from pathlib import Path

import pandas as pd

from payment_risk.marts import build_marts

results = Path("results")
run = json.loads((results / "run_info.json").read_text(encoding="utf-8"))
hourly, transactions = build_marts(
    pd.read_parquet(results / "clean_transactions.parquet"),
    start=pd.Timestamp(run["start"]),
    end=pd.Timestamp(run["end"]),
    out=Path("results_sql"),
    dsn=os.environ["PAYMENT_RISK_PG_DSN"],
)
print(len(hourly), len(transactions))
```

## Модели и бизнес-решение

**Временные ряды.** SARIMAX учитывает календарные сезонности, градиентный бустинг использует лаги, прошлые скользящие агрегаты и календарь. На каждой точке выпуска оцениваются сразу до 24 следующих часов, без фактических наблюдений из прогнозируемого блока. Выбор отдельного метода для каждого ряда сделан по MAE на первой части валидации. Для теста доступны MAE, RMSE и WAPE. Ряды измеряют число попыток, сумму и число наблюдаемых операционных риск-сигналов.

**Аномалии.** На второй части валидации калибруются верхние пороги остатков. В тесте превышения выводятся с оригиналом, прогнозом, отклонением и вкладом ведущей категории. Для расследования выбирается категория с наибольшим приростом по сработавшей метрике относительно того же часа прошлых недель. Для всплеска оборота дополнительно сравнивается средний чек. Доли риск-сигналов и отказов выводятся рядом как контекст. Метки fraud с задержкой не используются для оперативной сигнализации.

**Риск.** CatBoost и LightGBM обучены хронологически. В обучение входят зрелые метки, известные к его срезу. На момент выбора модели и порогов используются только зрелые валидационные метки для оценки потерь. В тесте действия вычисляются для всех поступлений, метрики классификации и финансовые результаты — по зрелым исходам. Сравниваются ROC-AUC, PR-AUC в форме average precision и recall/precision в верхних K скоринговых позиций. Модель выбирается по стоимости допустимой политики на валидации, с AP как дополнительным критерием.

**Пороги.** Для score `s` и порогов `r <= q` действует следующее правило.

| Условие | Действие |
| --- | --- |
| `s <= r` | Одобрить автоматически |
| `r < s <= q` | Передать на ручную проверку |
| `s > q` | Отклонить автоматически |

На валидации поиск проходит по всем наблюдаемым границам групп равного score. Доля review считается по всем валидационным поступлениям. Допустимый остаточный fraud loss измеряется как доля от сценария approve-all на зрелой части валидации. По умолчанию пределы составляют 6% review и 35% остаточного fraud loss. Стоимость проверки равна 2, штраф за ошибочное отклонение равен 12, review обнаруживает 80% мошеннического объёма и ошибочно отклоняет 2% легитимных операций, LGD равен 100%. Стоимости гипотетические и настраиваются через CLI.

В отчёте оптимизированная политика сопоставляется с approve-all на одинаковой зрелой выборке. Совокупные потери складываются из остаточного fraud loss, стоимости review и ожидаемого штрафа за false decline. Почасовой объём review оценивается как прогноз числа попыток, умноженный на валидационную долю review выбранной политики. Тест сравнивает эту оценку с фактической маршрутизацией модели. Агрегатное ограничение review на период допускает пики в отдельных часах.

На реальных данных ограничения зависят от полноты разметки, стоимости ошибок, действующего процесса авторизации и сезонности. Сценарий approve-all в этом проекте — контрфактическая симуляция на известных метках. Если отклонённые операции в реальной истории не получают исходов, оценка выборки может смещаться. Используйте зрелые когорты, измеренные параметры review и отдельное временное окно для проверки политики перед внедрением.
